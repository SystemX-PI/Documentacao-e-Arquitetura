01 · Fundamentos

Como o front está organizado

Uma aplicação de página única que atende o espaço da conta e a operação de consórcios pela mesma base de interface.

Stack principal

React 19TypeScript 6Vite 8React Router 7CSS

Lucide fornece ícones; qrcode.react desenha QR Codes de demonstração. O estilo combina folhas CSS próprias e o plugin Tailwind do Vite.

Responsabilidades

  • Renderizar as telas e guiar a navegação.
  • Validar dados de entrada e apresentar erros, carregamentos e confirmações.
  • Enviar e receber dados por endpoints REST.
  • Exibir o estado informado pela API, sem substituir regras do servidor.

04 · Recursos

Fluxos principais da conta

Cada tela combina estado de carregamento, validação, retorno de sucesso e mensagens de erro; ações críticas são confirmadas pela API.

Cadastro e sessão

  • Cadastro e login por e-mail e senha.
  • Login/cadastro Google via Google Identity Services quando o Client ID está configurado.
  • Recuperação de senha por código enviado pelo back-end.
  • Token de acesso e refresh token são mantidos localmente; o refresh rotativo é tentado diante de sessão expirada.
  • Falha definitiva da sessão dispara retorno à tela de login.

WhatsApp e Gmail

  • WhatsApp: solicitar QR, acompanhar estado e atualizar a conexão.
  • Gmail na conta: administrar caixas vinculadas conforme limites do plano.
  • Canal operacional Gmail: a rota administrativa solicita e-mail remetente e senha de app; apenas administrador pode salvar.
  • Limites e estado de conexão são exibidos a partir do contexto da conta.

Equipe, marca e perfil

  • Gerenciar membros conforme o perfil e os limites definidos pelo servidor.
  • Personalizar nome, logo e cores, com prévia na interface.
  • Atualizar foto; a interface aceita PNG/JPG/WebP de até 5 MB e reduz a imagem antes de enviar.
  • Configurações indisponíveis ao titular não são mostradas como ações válidas a outros perfis.

Plano e cobrança

  • A interface lê nível, limites, preço e configuração de pagamento do contexto fornecido pela API.
  • No modo de demonstração descrito pelo front, o teste inclui 1 WhatsApp e 1 Gmail por 3 dias; o plano Profissional demonstra 3 WhatsApps e 2 Gmails.
  • Com Stripe habilitado, a contratação redireciona para checkout hospedado e oferece cartão mensal ou Pix.
  • Sem Stripe, a simulação local pode demonstrar Pix/cartão fictícios sem mover dinheiro.
  • O estado profissional é confirmado pelo servidor; voltar do checkout não prova pagamento.
Importante sobre pagamentos: não use a tela de retorno do navegador como confirmação. A assinatura, os limites liberados e a ativação dependem do estado validado pelo back-end e do fluxo de webhook correspondente.

05 · Recursos

Fluxo operacional de consórcios

O front-end conduz a equipe pelo acompanhamento e pela comunicação; regras de transição, persistência e envio pertencem à API.

1 · Cadastrocliente, consórcio, grupo, cota e usuário
›
2 · Processocontemplação, responsável, status e documentos
›
3 · Comunicaçãoe-mail, WhatsApp, fila, tentativa e histórico
›
4 · Encerramentobaixa, auditoria e consulta pelo portal

Cadastros e contemplados

Listas paginadas, busca, consulta, edição e exclusão conforme permissões. Processos exibem status e permitem ações dentro das transições aceitas pelo back-end.

Comunicação e fila

Resumo por estado, filtros, tentativas por canal, histórico e reenvio. O front inclui chave de idempotência em ações de envio para que a API possa evitar duplicidade.

Disparo manual e reconciliação

Compor mensagens por processo/canal, acompanhar o resultado e tratar tentativas incertas conforme a resposta do servidor. Diagnósticos não substituem a reconciliação da operação.

Baixa, auditoria e portal

Acompanhar processos em encerramento, registrar eventos auditáveis e permitir que o beneficiário consulte somente os próprios processos e documentos autorizados.

Nota de domínio: a rota /app para administrar contas da plataforma não é a mesma área que /admin/clientes, destinada aos cadastros da operação de consórcios.

06 · Integração

Comunicação com a API

As telas usam serviços TypeScript compartilhados para manter autenticação, tratamento HTTP e contratos de chamadas consistentes.

CamadaUsoExemplos
services/http.tsFetch comum, JSON, cabeçalhos, timeout de 30 s e conversão de erros.401, 403, 409, 422, 429 e falhas de rede.
services/auth.tsCadastro, login, logout, recuperação, refresh e sessão./api/auth/login, /google, /refresh.
services/backend.tsEndpoints da operação e das integrações./api/integracoes/whatsapp/qr, /api/processos-contemplacao.
services/platform.tsContexto multi-conta e dados da plataforma./api/platform/context, clientes, canais e assinatura.

Comportamento de sessão e falhas

  • As requisições autenticadas usam Authorization: Bearer com o token atual.
  • Em 401, o cliente tenta renovar uma vez com refresh token; se a renovação falhar, limpa a sessão e avisa as rotas.
  • Timeout e indisponibilidade de rede recebem mensagens distintas; a interface evita afirmar sucesso quando não recebeu confirmação.
  • Erros de validação podem ser associados aos campos; as páginas exibem feedback próximo à ação.

Configuração do endpoint

VariávelFinalidadeObservação
VITE_API_URLPrefixo opcional para chamadas HTTP.Vazia usa a mesma origem e o proxy.
VITE_API_PROXY_TARGETDestino de /api no Vite dev.Padrão local: http://localhost:8080.

07 · Operação técnica

Configurar, executar e verificar

A execução integrada via Docker é o caminho recomendado. Para desenvolvimento de interface, o Vite inicia o front isoladamente.

Pilha completa com Docker

cd Back-end
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# Preencha os valores locais no .env
docker compose --profile full up --build -d --wait --wait-timeout 600

O perfil completo compila e inicia front, API, MySQL e serviços de integração. Padrões do projeto: front 5173, API/Swagger 8080, MySQL 3307, Evolution 8081. Portas podem ser alteradas no `.env` se já estiverem ocupadas.

Vite local

cd Front-End
npm ci
npm run dev

Abra a origem mostrada pelo Vite, normalmente http://localhost:5173. Para outra API local, defina VITE_API_PROXY_TARGET. O repositório também fornece scripts de início com Docker.

Comandos de qualidade

npm run build       # TypeScript + pacote de produção
npm run lint        # análise estática com Oxlint
npm run test:ui     # Playwright com Vite isolado em 5174

Os testes reais contra API/banco usam configuração separada, schema descartável, conta fictícia e portas próprias; não devem receber credenciais nem dados de produção. A suíte Stripe exige ambiente isolado e cartão oficial de teste.

Atalhos de rota: o Nginx do Docker mantém fallback para rotas da SPA. Após mudança de código, reconstrua a imagem do front; reiniciar apenas o navegador não atualiza o bundle.
